## 1. Цель и результат

Приложение для задач, работающее с API по HTTP: загрузка и фильтрация, создание, редактирование, изменение статуса, удаление и восстановление 12 исходных задач. Данные хранятся на сервере в оперативной памяти и переживают перезагрузку браузера, но не перезапуск сервера.

## 2. Окружение и запуск

Методичка рекомендует **Node.js 24 LTS**. Код фактически проверен также на **Node.js v22.16.0**, npm **10.9.2**. В WebStorm расположить `practice-06` рядом с `practice-05`, открыть терминал в папке практики:

```bash
cd practice-06
npm start
```

Открыть в браузере:

- Приложение: **http://127.0.0.1:5506/**
- Индивидуальный фильтр: **http://127.0.0.1:5506/?dataset=variant**
- Браузерные проверки: **http://127.0.0.1:5506/checks.html**
- API: **http://127.0.0.1:5505/api/health**

`npm start` запускает **два сервера**. Не открывать `index.html` как `file://`. Устанавливать пакеты не требуется. Остановка: `Ctrl+C`. Если порты заняты:

```bash
node tools/start.mjs 5515 5516
```

Тогда приложение: `http://127.0.0.1:5516/?api=http://127.0.0.1:5515/api`.

### Асинхронные состояния

`loading` — запрос ещё идёт, установлен `aria-busy="true"`; `ready` — список получен и непустой; `empty` — успешный ответ без совпадений; `error` — проблема загрузки, есть текст и кнопка повторного запроса.

После успешных `POST/PATCH/DELETE` контроллер снова отправляет `GET /tasks` с текущими фильтрами. Данные не записываются в `localStorage`. Это соответствует принципу «сервер — источник истины».

### Защита от конкурирующих запросов

Перед повторной загрузкой вызывается `AbortController.abort()` для предыдущего запроса. В дополнение используется порядковый `loadSequence`: результат применяется только если его номер совпадает с последним. Даже если тестовый/кэширующий клиент проигнорирует отмену, устаревший ответ не перерисует список. Отмена не показывается пользователю как ошибка.

### Безопасный интерфейс

Названия и категории добавляются только через `textContent` (не `innerHTML`); карточки — `li.task-card` с `data-task-id` и кнопками `toggle`, `edit`, `delete`. Некорректная форма отклоняется **до отправки POST**, а `aria-invalid` и сообщения полей дают обратную связь. При мутациях кнопки временно блокируются.

## 7. Ответы на контрольные вопросы

1. **Почему 404 не rejected?** `fetch` отклоняется из-за сбоя сети или отмены, а 404 — полученный HTTP-ответ.
2. **Порядок разбора?** Сначала `response.ok`, затем `204`, потом `Content-Type`, затем `response.json()`.
3. **POST и PATCH?** POST создаёт новую запись; PATCH изменяет существующие поля.
4. **201 и Location?** 201 сообщает об успешном создании, Location указывает на новый ресурс.
5. **Почему нельзя JSON при 204?** У 204 отсутствует тело, `json()` вызовет ошибку разбора.
6. **Зачем CORS preflight?** Браузер уточняет разрешённые методы/заголовки для запросов между origin; `no-cors` не позволяет читать JSON.
7. **empty vs error?** empty — нормальный результат 200 с пустым массивом, error — сбой загрузки.
8. **Почему не localStorage?** Изменения хранит и подтверждает API.
9. **Зачем повторный GET?** Отобразить только серверное подтверждённое состояние и текущие фильтры.
10. **Гонка запросов?** Первый, более долгий запрос может завершиться после второго.
11. **Зачем последовательный номер?** Некоторые источники не реагируют на отмену, но результат всё равно устаревает.
12. **Почему не показывать aborted?** Отмена при смене фильтра — ожидаемое действие пользователя.
13. **Что валидирует клиент и сервер?** Клиент форму для обратной связи; сервер все поля и права независимо от клиента.
14. **Зачем передаётся view?** Чтобы изолировать логику от DOM и тестировать контроллер без браузера.
15. **Зачем textContent?** Оно выводит недоверенный текст буквально и не исполняет HTML.
